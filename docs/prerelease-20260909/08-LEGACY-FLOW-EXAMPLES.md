## Вещи — WISH-01

В исходном аудите найдены обе оболочки и отмечено объединение overview/detail. Теперь фиксируем точный дефект взаимодействия:

`ProductionJourney` → onAddThing → `openJourneyDetail('things')` + `setThingCaptureOpen(true)` → `WatercolorScreen` → `PaperSheet` с формой. Источники: app/page.tsx:4365,4375,4724,4732.

Одно действие «добавить» меняет не только состояние, но и экранный/компонентный язык. Форма одновременно раскрывает название, категорию, причину и планирование; изменение существующей позиции использует ещё одну inline-форму.

**Целевое поведение:** добавление в контексте списка. Название — основной ввод; дополнительные сведения и дата по желанию. После сохранения тот же список с добавленной позицией. Редактирование использует тот же компонент полей и поведение сохранения/отмены. Конкретный контейнер (inline/panel) проверяем в прототипе с клавиатурой, не выбираем только по внешнему виду.

**DoD:** add/edit/error/retry/cancel/reopen не открывают старую Watercolor-оболочку; ввод сохранён при ошибке; результат появляется один раз; возврат сохраняет список. Не создавать напоминание без намерения пользователя и не обещать выключенную Telegram-доставку.

## Характер — PRO-02

В первом аудите учтены экран и редактор, но проблема несовпадения показанного управления и редактирования была описана недостаточно конкретно. Запись в реестре сама по себе не означает, что UX этой ветки принят.

`ProfileMemoryWorkspace.tsx:261–267`: шкалы — декоративные div, каждая строка вызывает один `openEditor('character')`. Строка «Общительность» показывает socialMode, но этот редактор не содержит socialMode: его поле в редакторе social (342). То есть переход с конкретной характеристики не гарантирует даже нужного поля.

`traitPosition`, строка107: позиция выводится из ключевых слов текста как36/68/78%, иначе50%, включая отсутствие значения. Это не сохранённая числовая оценка. Нельзя просто включить drag у шкалы и записывать проценты в существующие категориальные поля.

**Целевое поведение:** менять конкретную характеристику там, где она показана. Для текущих категориальных значений — подписанный выбор в той же строке, без общей анкеты. Если продукту действительно нужна шкала — отдельно определить её смысл, набор значений, неопределённое состояние и хранение. Не показывать «не заполнено» как среднее значение. Не смешивать темперамент с уверенностью и энергию с возбудимостью без явного продуктового контракта.

**DoD:** каждая характеристика открывает управление именно своим полем; нет перехода к общей форме ради одного значения; ошибка/сохранение/отмена в контексте; соседние значения не меняются; после reload тот же факт, без выдуманной числовой точности. Проверить все четыре строки, включая Общительность.

## Дополнение к B-06 и приёмке

Для каждого действия проверять не только достижимость destination, но соответствие обещания управления: что пользователь ожидает изменить → какое поле действительно редактирует → какой объект сохраняется. Единые цвета и скругления не исправляют неправильную модель взаимодействия. Добавлены конкретные подслучаи WISH-01:add/edit и PRO-02:each-trait для B-06; прежние33 сценария не переименовываются и не считаются пройденными.
