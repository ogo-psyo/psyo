# Сервис Псё: контракт нового интерфейса

Статус: **спроектировано для реализации, не реализовано в production**. Основание: комментарии Руслана 09.09.2026 + аудит кода c15d067. Новый визуальный язык не меняет источники данных. Требования ниже заменяют устаревшие визуальные указания `DESIGN_DIRECTION.md` для данного выпуска, но не его правила приватности и продуктовой честности.

## 1. Обещание продукта

Выразить задачу, выполнить действие и вернуться к результату — без повторного ввода, потери данных и обязательного разговора с ИИ. Для каждой собаки понятны её сведения, записи, дела и прогулки. Не обещать живой поиск, гарантированную совместимость собак, ветеринарный диагноз или доставку уведомления на основании красивого экрана.

Единица готовности — **законченный сценарий со всеми достижимыми ветками**, а не верхнеуровневая страница. Одна и та же сущность открывается и редактируется одинаково из любого входа.

## 2. Информационная архитектура: один дом объекта

Предлагаем сохранить пять входов последнего прототипа, но убрать дублирование меню «Всё» и Профиля.

| Раздел | Ценность | Содержит | Не становится |
|---|---|---|---|
| Псё | Выразить задачу или продолжить разговор | Ввод, последние разговоры при их наличии, контекст выбранной собаки; переход к конкретному черновику/объекту | Обязательным посредником для любого действия, списком всех возможностей |
| Карта | Выбрать место, собрать или записать прогулку | Места, поиск, зоны, подборки, планы, записанные маршруты, экспорт/доступ | Списком первых сохранённых мест под названием «рядом» |
| Гав | Найти компанию и понять состояние знакомства | Живые сигналы, анкеты, своя публичная анкета, отклики, связи, предложения мест | Автоматическим отправителем отклика по свайпу, чатом с выдуманным принятием |
| Всё | Прямо открыть регулярную задачу | Уход (календарь/дела), Привычки, История, Документы, Покупки | Копией Профиля; вторым самостоятельным хранилищем сохранённых объектов |
| Профиль | Управлять идентичностью собаки и доступом | Паспорт, характер/особенности, фото/образ, публичная карточка, переключение собак, настройки аккаунта; память помощника только при готовности её сервиса | Вторым оглавлением истории/документов/карты/знакомств |

**Основные дома:** наблюдения → Всё/История; дела → Всё/Уход; привычки → Всё/Привычки; документы → Всё/Документы; покупки → Всё/Покупки; места/подборки/маршруты → Карта/Сохранённое; связи → Гав/Отклики; профиль/приватность → Профиль.

Контекстный вход допустим: «Документы Плутона» из паспорта открывает тот же список с petId, а не отдельный экран-двойник. В Профиле он вторичный, не повтор всего меню. Возврат ведёт туда, откуда пришли. В «Всё» не нужно ещё одно «Сохранённое», объединяющее несвязанные документы, маршруты и ответы без понятного типа.

История — представление событий, а не копия таблиц. Элемент несёт `entityType + entityId + petId`; время события отдельно от времени создания. Список должен объяснять ограничение периода/подгрузку, а не выдавать последние 12/20 строк за всю историю. Сохранённые ответы агента — в истории/результатах разговора с типом «Ответ», не маршрут без геометрии и не медицинский факт автоматически.

## 3. Контракт перехода

Единая модель адреса: `{screen, petId, entityType?, entityId?, mode?, origin, listState?, draftId?}`. `origin` хранит реальный источник входа; `listState` — фильтр/дата/прокрутка, для карты также camera/selectedPlace. Это проектируемый клиентский контракт, не новая БД.

- Навигация вперёд добавляет уровень, отмена возвращает к источнику; успешное создание заменяет форму на результат по полученному ID.
- Back Telegram, браузера и кнопка «Назад» используют один контракт. Не три разных стека.
- Результат открывается по ID; перезагрузка не должна превращать просмотр в новую форму. Нет прав/объект удалён → объяснение и возврат в родительский раздел.
- После смены собаки отменяются/игнорируются поздние ответы для прежней; запросы, кеши и черновики имеют ownerId/petId scope. Не отправлять черновик другой собаке.
- Отмена чистого черновика — сразу; изменённого — выбор «Продолжить / Выйти без сохранения» или проверенное восстановление черновика. Уже отправленный запрос нельзя «отменить» только закрытием формы.
- У повторяемой команды один стабильный requestId, неизменяемое тело и eventTime. Исправление тела создаёт новый запрос, но не новый доменный объект при редактировании.
- При неопределённом результате сети UI показывает «Проверяем сохранение», выясняет судьбу requestId, затем предлагает повтор. Нельзя объявлять отсутствие записи только по timeout.
- Успех = ID/версия от сервера; localStorage в аккаунтном режиме не подтверждает облачное сохранение.
- Клавиатура не закрывает результат и основной CTA; навигация и формы учитывают safe-area/visualViewport. Фокус возвращается к исходному элементу без скачка списка.

## 4. Главные сквозные сценарии

### A. Записать состояние

Входы: свободный текст на Псё; «Добавить запись» в Истории; профиль/контекст дня; голос при доступном сервисе.

«Хочу отметить состояние» → чистый черновик. Текст с фактом → исходные слова уже в черновике. Основная запись свободным текстом не требует выдумывать нормальные значения показателей. Дополнительные поля раскрываются по желанию. Распознавание предлагает кандидаты, но не выдаёт их за подтверждённые факты. Исходный текст и происхождение не теряются.

Сохранить → результат с датой события, собакой, текстом, «Изменить / В историю». Удалить → подтверждение/восстановление по существующему контракту; отмена не создаёт новую запись. Если пользователь пришёл из разговора, возврат сохраняет разговор и ссылку на запись. Нет обязательной промежуточной анкеты Профиля.

### B. Уход и привычки

Календарь/список → существующее дело или создание → название, нужная дата, режим времени, повтор → проверка → сохранённое дело → выполнить/перенести/изменить/удалить → история. Точное время не подставлять как осознанный выбор пользователя. Повтор генерируется сервером атомарно с выполнением; двойное выполнение не создаёт два следующих дела.

Привычка — цель на период, не бесконечная цепь напоминаний. Создать/изменить/отметить/архивировать; прогресс пересчитывается на одинаковой временной зоне. Существующие привычки не исчезают из-за упрощения меню.

Доставка в Telegram — отдельное состояние сервиса. При текущем `telegram_notifications_enabled=false` нельзя писать «напомним в Telegram» как работающую функцию. Дело в плане остаётся полезным само по себе.

### C. Места и прогулки

Поиск/подборка/карта → выбранное место с привязанной точкой → сохранить отдельно или добавить в **тот же** план. Карта и список показывают одинаковый набор; возврат не сбрасывает камеру. Подборка — набор ссылок на места, не папка без связи с картой.

План → порядок остановок/удаление/добавление → расчёт или явно ручной путь → сохранение → открытие/редактирование/GPX/доступ. При неудаче расчёта остаются остановки; последняя успешная геометрия помечена устаревшей, не выдаётся за новый расчёт.

Запись прогулки отдельна от планирования: разрешение геолокации → запись → пауза/потеря сигнала → продолжение → завершение → просмотр разрывов → сохранение. Не соединять потерянные сегменты выдуманной прямой. Закрытие/фон/возврат проверяются отдельно в Telegram.

### D. Гав

Два режима сохраняются: «Гуляют сейчас» и «Знакомства». Геолокация отклонена → ручной район, не пустая выдача. Фильтр без совпадений отличается от сетевого сбоя.

Анкета/сигнал → явный отклик → ожидание → принят/отклонён/отменён/истёк/закрыт → связь; контакт только при разрешённом состоянии и проверенном источнике. Свайп только листает. Жалоба и блокировка доступны в контексте, скрывают недопустимые контакты/предложения.

**Первый релиз нового дизайна:** связь → выбрать сохранённое место/маршрут → посмотреть именно публикуемые сведения → подтвердить отправку → «Предложение отправлено». Это соответствует текущему backend. Макетное «место подтверждено» исключено из первого выпуска. Ответ на предложение требует новой версии сущности и отдельной приёмки двух владельцев (задача B-08), а не смены UI-флага.

### E. Документы и профиль

Документы: пустой список → выбор файла → название/тип/дата/клиника → загрузка → сохранённый объект → открытие → истёкшая ссылка/повтор → удаление и завершение очистки. В первом выпуске не обещаем OCR или чтение содержимого агентом: в PR29 поиск документов ограничен метаданными.

Профиль: выбранная собака → паспорт/характер/взаимодействие → редактирование → атомарное сохранение → обновлённый просмотр. Приватный характер и публичная анкета не одно хранилище: публикация не следует автоматически за изменением приватного поля.

Фото: выбор → проверка файла → черновик → явное применение/отмена → активное изображение; неудачная генерация/загрузка не стирает прежнее. Изображение целиком/контролируемая кадрировка, без требования идеального пользовательского кадра. Публичная версия создаётся по существующему разрешению, не из приватной ссылки.

### F. Покупки

Добавить название → сохранить → изменить/куплено/вернуть/удалить/восстановить. «Добавить в план на дату» — отдельное явное действие: оно может атомарно создать связанное дело. Простое добавление покупки не создаёт дело на завтра. При отмене/удалении связанного дела объяснить судьбу покупки, не удалять другой объект молча.

## 5. Память: не подмена источников

В текущем production `ProfileMemoryWorkspace` — профиль, черты, паспорт, история и ввод наблюдений; это не универсальный список памяти агента. В PR29 память — отдельный невыпущенный сервис.

В будущем экране показывать тип, значение, источник, дату, petId, состояние. Поле профиля редактируется в своём редакторе, запись — в записи, отдельное предпочтение — в памяти. Ветка PR29 поддерживает свои команды correction/forget; точную семантику исключения источника из контекста проверить, не заменять простым скрытием карточки. Забытый факт не должен восстанавливаться на следующем сборе контекста из того же источника без нового действия владельца. При этом удаление предпочтения не должно незаметно удалять медицинский документ.

R1 не включает новый пункт памяти с неработающими кнопками. Когда R3 готов — профиль открывает список → факт → изменение/забыть → результат, пустой список, ошибка, конфликт, повтор и возврат.

## 6. Материал и дизайн-система

NarisovanniySANS на выразительных заголовках; нейтральный читаемый шрифт на полях, числах, датах и ошибках. Шрифт известен и загружен для примерки; права на коммерческое встраивание и webfont пока не подтверждены, это задача выпуска, не причина подменять шрифт молча.

Единые компоненты: ScreenFrame, AppNavigation, Header/Back, DraftForm, Field/Error, AsyncAction, EntityResult, Empty/Unavailable, Confirm/Undo, DocumentViewer, PhotoFrame, StatusLine. Это желаемые роли, не обязательные новые имена файлов. Использовать/адаптировать `components/ui/*` вместо второй независимой библиотеки.

Один scroll-container на поверхность; вложенные панели не конкурируют. Один основной CTA на шаг. Связанные заголовок и ввод рядом, воздух вокруг группы. Стекло выборочно на плавающих элементах, непрозрачная альтернатива без blur. Никакой анимации ради ожидания; reduced-motion; тексты/длинные значения не обрезаются фиксированной высотой.

Существующие 10 глобальных CSS-входов в `app/layout.tsx` не дополнять одиннадцатым слоем случайных overrides. Новые поверхности изолированы выбранной областью/токенами, старые стили продолжают обслуживать только старую версию. Удаление старых правил — после доказательства отсутствия достижимых потребителей.
